# ADR-0004: 배송 정보는 매칭 단위로만 보관하고 30일 후 삭제

**Date**: 2026-11-15
**Status**: accepted
**Deciders**: 프로젝트 오너, Claude

## Context

교환하려면 받는 사람의 이름, 주소, 전화번호가 보내는 사람에게 전달되어야 한다. 이것이 구양이가 다루는 가장 민감한 정보이고, 모르는 사람끼리의 교환이라 노출 범위와 보관 기간이 곧 신뢰다. 한편 미발송 분쟁을 처리하려면 교환이 끝난 직후에 바로 지울 수는 없다. 사용자 중에는 청소년도 있다(가입은 만 14세 이상).

## Decision

1. 배송 정보는 **매칭마다 입력**하고 그 매칭에만 묶어 저장한다 (`shipping_addresses`, PK `(match_id, user_id)`). 프로필에 기본 주소를 저장하지 않는다.
2. 수락할 때 입력하되, **전원이 수락해 성사된 뒤에만**, **그 사람에게 물건을 보내는 사람에게만** 보인다. 같은 매칭의 다른 참여자와 운영자 화면에는 보이지 않는다.
3. 제안이 거절·만료되면 **즉시 삭제**한다. 교환이 완료되거나 분쟁 후 취소되면 **30일 뒤** 배송 정보와 송장 정보를 삭제한다 (pg_cron).
4. 보관 기간은 `app_settings.shipping_retention_days` 로 둔다.

## Alternatives Considered

### 대안 1: 프로필에 기본 주소 저장 + 매칭마다 복사
- **Pros**: 매번 입력하지 않아도 된다.
- **Cons**: 교환하지 않는 동안에도 주소가 계속 남는다. 유출 시 피해 범위가 전체 사용자로 커지고, "30일 후 삭제" 가 반쪽이 된다.
- **Why not**: 입력 편의는 브라우저 자동 완성으로 대부분 해결되고, 상시 보관의 위험은 해결할 방법이 없다.

### 대안 2: 서비스에 저장하지 않고 당사자끼리 외부(X DM 등)에서 교환
- **Pros**: 서비스가 개인정보를 갖지 않는다.
- **Cons**: 3자 순환에서 누가 누구에게 보내는지 사용자가 직접 챙겨야 하고, 분쟁 때 확인할 기록이 없다. 서비스 밖으로 나가는 순간 이탈한다.
- **Why not**: 해결하려는 문제(수동 조율)를 다시 사용자에게 넘긴다.

### 대안 3: 컬럼 암호화 (Vault / pgsodium) 추가
- **Pros**: DB 덤프가 유출되어도 주소가 평문이 아니다.
- **Cons**: 키 관리와 복호화 함수가 늘고, 키가 같은 프로젝트에 있어 막아 주는 범위가 제한적이다.
- **Why not**: MVP 에서는 RLS + 최소 보관으로 시작한다. 사용자가 늘면 다시 검토한다.

## Consequences

### Positive
- 평소에 서비스에 남아 있는 주소는 진행 중이거나 최근 30일 안에 끝난 교환의 것뿐이다.
- 3자 순환에서도 각자 한 사람의 주소만 본다.
- 개인정보 처리방침에 수집 항목, 목적, 보관 기간을 단순하게 쓸 수 있다.

### Negative
- 교환할 때마다 주소를 입력해야 한다.
- 수락 단계에서 주소를 받으므로 수락의 문턱이 조금 높아진다.
- 30일이 지나면 운영자도 분쟁 내용을 확인할 수 없다. 신고는 그 안에 해야 한다.

### Risks
- **RLS 정책 실수로 다른 참여자에게 노출** → "내가 보내지 않는 참여자의 주소는 볼 수 없다" 를 필수 테스트로 둔다.
- **삭제 작업이 조용히 실패** → 보관 기한이 지난 행 수를 운영자 화면에 표시하고, 0 이 아니면 경고한다.
- **백업에 남는 정보** → Supabase 백업 보관 기간을 확인해 처리방침에 적는다.
