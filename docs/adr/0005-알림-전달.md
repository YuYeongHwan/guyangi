# ADR-0005: 알림은 Edge Function 이 웹 푸시와 이메일로 보낸다

**Date**: 2026-11-15
**Status**: accepted
**Deciders**: 프로젝트 오너, Claude

## Context

매칭 제안에는 24시간 응답 기한이 있고, 놓치면 무응답 횟수가 평판에 남는다. 발송 기한(48h 경고, 72h 분쟁)도 마찬가지다. 앱을 열어야 보이는 인앱 알림만으로는 기한을 지키기 어렵다. 웹 푸시는 iOS 에서 홈 화면에 추가한 PWA 에만 오므로 푸시만으로도 부족하다. 한편 알림은 DB 함수와 pg_cron 안에서 만들어지는데, 푸시와 이메일은 DB 밖으로 HTTP 요청을 보내야 하고, 보내려면 다른 사용자의 이메일과 푸시 구독을 읽어야 한다.

## Decision

1. 채널은 인앱(Realtime) + 웹 푸시(VAPID) + 이메일(Resend). 기한이 걸린 알림(수락 요청, 발송 기한 경고, 분쟁 전환)은 푸시와 이메일 모두, 그 외는 인앱과 푸시만 보낸다.
2. 알림 행은 DB 함수가 `notifications` 에 넣는다. insert 에 건 Database Webhook 이 Supabase Edge Function `send-notification` 을 부르고, 이 함수가 푸시와 이메일을 보낸 뒤 결과를 행에 기록한다. 실패분은 pg_cron 이 3회까지 다시 부른다.
3. **service role 키의 보관 범위를 "매처" 에서 "매처 + Edge Function" 으로 넓힌다.** 웹(Vercel)에는 여전히 두지 않는다. Resend API 키와 VAPID 비밀 키도 Edge Function secret 으로 둔다.
4. 로그인 제공자가 이메일을 주지 않으면 알림용 이메일을 직접 입력받아 확인 링크로 인증한 뒤에만 쓴다. 입력은 건너뛸 수 있다.

키 범위를 넓히는 이유: 발송하는 쪽은 수신자 본인의 세션 없이 그 사람의 이메일(`notification_settings`, 본인만 읽을 수 있음)과 푸시 구독을 읽어야 한다. RLS 를 우회할 권한이 어딘가에는 필요하고, 그 자리로 Supabase 프로젝트 안에서 도는 Edge Function 이 웹 서버보다 좁다. 키가 Supabase 밖으로 나가지 않고, 함수가 하는 일이 "알림 한 건 발송" 하나뿐이다.

## Alternatives Considered

### 대안 1: Next.js 라우트 핸들러(Vercel)에서 발송
- **Pros**: 웹과 같은 코드베이스, 같은 언어, 로컬 개발이 쉽다.
- **Cons**: 웹 서버가 service role 키를 갖게 된다. 웹은 사용자 입력을 직접 받는 곳이라 키가 노출될 길이 가장 많다.
- **Why not**: "웹에는 service role 키를 두지 않는다" 는 경계를 지키는 쪽이 더 중요하다.

### 대안 2: 매처 cron 이 미발송 알림을 모아서 발송
- **Pros**: 키가 이미 있는 곳이라 범위가 넓어지지 않는다. 새 구성 요소가 없다.
- **Cons**: 10분 주기에 GitHub Actions 지연까지 더해진다. 매처가 멈추면 알림도 멈춘다. 매처의 역할이 "제안만 한다" 에서 벗어난다.
- **Why not**: 기한 알림은 늦으면 의미가 없다.

### 대안 3: DB 에서 직접 발송 (pg_net 으로 Resend·푸시 서버 호출)
- **Pros**: 구성 요소가 가장 적다.
- **Cons**: 웹 푸시는 VAPID 서명과 페이로드 암호화가 필요해 SQL 로 구현하기 어렵다. API 키를 DB 안에 보관해야 한다.
- **Why not**: 푸시를 SQL 로 보낼 수 없다.

### 대안 4: 이메일만 (푸시 없음)
- **Pros**: 가장 단순하고 모든 기기에 닿는다.
- **Cons**: 메일함을 자주 보지 않는 사용자에게는 늦게 닿는다. 발송량이 늘어 Resend 한도를 빨리 쓴다.
- **Why not**: 모바일 사용자에게는 푸시가 가장 빠르다. 이메일은 보완 수단으로 둔다.

## Consequences

### Positive
- 앱을 열지 않아도 기한 알림이 닿는다. iOS 에서 PWA 를 설치하지 않은 사용자도 이메일로 받는다.
- 알림을 만드는 일(DB 함수)과 보내는 일(Edge Function)이 나뉘어, 발송이 실패해도 상태 전이는 영향을 받지 않는다.
- 웹 서버는 여전히 사용자 세션 권한만 갖는다.

### Negative
- 구성 요소가 하나 늘고 실행 환경이 셋이 된다 (Node, Python, Deno).
- service role 키를 가진 곳이 둘이 된다.
- 이메일 발신 도메인, DNS 인증, Resend 한도, 수신 거부 처리를 운영해야 한다.

### Risks
- **Edge Function 이 외부에서 호출됨** → Webhook 이 붙이는 비밀 헤더를 확인하고, 없으면 거부한다. 함수는 요청 본문의 알림 id 만 믿고 나머지는 DB 에서 다시 읽는다.
- **알림에 개인정보가 실림** → 푸시와 이메일 본문에 배송 정보를 넣지 않는다. 내용은 "무슨 일 + 기한 + 링크" 뿐이다.
- **같은 알림이 두 번 발송됨** → 발송 전에 `push_sent_at` / `email_sent_at` 을 확인하고, 재시도는 3회로 제한한다.
- **만료된 푸시 구독이 쌓임** → 푸시 서버가 404/410 을 주면 그 구독을 삭제한다.
- **Resend 무료 한도 초과** → 이메일은 기한 알림 세 종류에만 쓴다. 출시 전 한도를 확인한다.
- **이메일 오입력으로 남에게 발송** → 확인 링크로 인증된 주소에만 보낸다.
- **카카오 로그인에서 이메일을 받지 못함** → Supabase 카카오 제공자에서 이메일 없는 사용자를 허용하는 설정을 Sprint 2 에서 확인한다.
