# ADR-0002: 매칭 엔진을 Python 서비스로 분리

**Date**: 2026-11-15
**Status**: accepted
**Deciders**: 프로젝트 오너, Claude

## Context

매칭은 "누가 가진 것을 누가 원하는가" 그래프에서 길이 2와 3의 순환을 찾고, 서로 겹치지 않는 조합을 고르는 문제다. 사용자 1000명 규모에서 수 초 이상 걸릴 수 있고, 잘못된 제안(같은 사용자 중복, 수량 초과)은 실제 교환 사고로 이어지므로 알고리즘을 독립적으로 촘촘하게 테스트해야 한다. 웹은 Vercel 서버리스에서 돌아 실행 시간이 제한된다.

## Decision

매칭 엔진을 `services/matcher` 의 Python 서비스로 분리한다 (networkx, pytest). 매처는 DB 뷰를 읽고 `propose_match` 함수만 호출하며, 테이블을 직접 쓰지 않는다.

## Alternatives Considered

### 대안 1: Next.js 안에서 TypeScript 로 구현
- **Pros**: 언어 하나, 타입 공유, 배포 하나.
- **Cons**: 서버리스 실행 시간 제한에 걸리고, 그래프 알고리즘 라이브러리와 테스트 도구가 Python 보다 빈약하다.
- **Why not**: 배치 계산을 요청-응답 환경에 넣게 된다.

### 대안 2: SQL 만으로 구현 (조인·재귀 CTE)
- **Pros**: 추가 서비스가 없고 데이터 옆에서 돈다.
- **Cons**: 1:1 은 조인으로 되지만, 3자 순환에서 "겹치지 않는 조합을 우선순위대로 고른다" 를 SQL 로 쓰면 읽기도 테스트하기도 어렵다.
- **Why not**: 가장 사고 위험이 큰 로직이 가장 검증하기 어려운 형태가 된다.

### 대안 3: Supabase Edge Function
- **Pros**: 같은 플랫폼 안에서 돈다.
- **Cons**: 실행 시간·메모리 제한, Deno 환경에서 그래프 라이브러리 선택지가 적다.
- **Why not**: 대안 1과 같은 제한을 받는다.

## Consequences

### Positive
- 알고리즘을 DB 없이 순수 함수로 테스트할 수 있다 (사이클 유효성, 사용자 중복 금지, 수량 초과 금지, 1000명 성능).
- 실행 시간 제한이 없고, 실행 방식(cron → queue)을 웹과 무관하게 바꿀 수 있다.
- 매처에 버그가 있어도 `propose_match` 가 다시 검증하므로 잘못된 제안이 DB 에 들어가지 않는다.

### Negative
- 언어와 도구가 둘이 된다 (pnpm + uv, 린트·테스트·CI 각각).
- TypeScript 타입을 공유하지 못한다. 뷰 3개와 함수 1개의 형태가 계약이 되므로, 바꿀 때 양쪽을 함께 고쳐야 한다.

### Risks
- **뷰·함수 계약이 어긋남** → 매처 통합 테스트를 로컬 Supabase 에 대해 돌린다.
- **service role 키 유출** → 매처(GitHub Actions secret)에만 둔다. 웹에는 두지 않는다.
