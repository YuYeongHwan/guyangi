# ADR-0003: 매처 실행은 cron 배치로 시작

**Date**: 2026-11-15
**Status**: accepted
**Deciders**: 프로젝트 오너, Claude

## Context

매처를 언제 돌릴지 정해야 한다. 도감이 바뀔 때마다 바로 돌리면(이벤트·큐) 제안이 빠르지만 큐, 워커 상시 실행, 중복 실행 방지가 필요하다. 교환은 택배로 며칠이 걸리는 일이라 제안이 몇 분 늦어도 사용자 경험에 큰 차이가 없고, 초기 사용자는 500명 수준이다. 한편 응답 기한 만료와 발송 기한 경고는 매칭 계산과 무관하게 제때 돌아야 한다.

## Decision

매처는 GitHub Actions 예약 실행으로 10분마다 전체 배치를 돈다. 기한 처리(만료, 경고, 분쟁 전환, 배송 정보 삭제)는 매처와 분리해 Postgres 안의 pg_cron 이 5분마다 `run_timers()` 를 부른다.

## Alternatives Considered

### 대안 1: 큐 기반 (도감 변경 → 큐 → 상시 워커)
- **Pros**: 제안이 거의 즉시 나온다. 바뀐 사용자 주변만 계산하면 된다.
- **Cons**: 워커를 항상 띄울 곳, 큐, 재시도·중복 처리, 부분 계산의 정합성 검증이 필요하다.
- **Why not**: 사용자 500명에서 얻는 것은 몇 분의 지연 단축뿐인데 운영할 것이 크게 늘어난다.

### 대안 2: 기한 처리도 매처 cron 에서 함께
- **Pros**: 예약 작업이 한 곳에 모인다.
- **Cons**: GitHub Actions 예약 실행은 지연되거나 건너뛸 수 있고, 매처가 실패하면 만료 처리도 멈춘다.
- **Why not**: 예약 해제와 배송 정보 삭제는 매처 상태와 무관하게 보장되어야 한다.

### 대안 3: pg_cron 이 매처까지 호출
- **Pros**: 예약이 DB 한 곳에서 관리된다.
- **Cons**: 매처를 HTTP 로 부를 수 있게 상시 호스팅해야 한다.
- **Why not**: 초기에는 호스팅할 서버를 두지 않는다.

## Consequences

### Positive
- 서버·큐 없이 시작한다. 매처는 매번 전체를 다시 계산하므로 상태가 없고 디버깅이 쉽다.
- 매처가 멈춰도 기한 처리와 개인정보 삭제는 계속된다.

### Negative
- 도감을 입력한 뒤 제안까지 최대 10분 이상 걸린다.
- 전체 재계산이라 사용자 수가 늘면 실행 시간이 늘어난다.

### Risks
- **GitHub Actions 예약 실행은 지연되거나 건너뛸 수 있다** → 그래서 시각이 중요한 기한 처리(만료, 발송 경고, 분쟁 전환, 자동 수령, 배송 정보 삭제)는 매처가 아니라 pg_cron 이 맡는다. 매처가 늦으면 제안이 늦어질 뿐, 기한과 예약 해제는 어긋나지 않는다.
- **저장소에 60일간 활동이 없으면 예약 워크플로가 자동으로 꺼진다** → `matcher_runs` 에 실행 시각을 기록하고, 마지막 실행이 30분을 넘으면 운영자 화면에 경고를 띄운다. 꺼졌으면 Actions 화면에서 다시 켠다. 개발이 멈춘 운영 기간에는 달력에 50일 주기 확인 일정을 둔다.
- **실행 시간 한도** → 10분 간격이면 한 달 약 4,300회 실행이다. 공개 저장소는 표준 러너가 무료라 저장소를 공개로 둔다.
- **공개 저장소에 비밀 값이 들어감** → 아래 규칙.
- **두 실행이 겹침** → 워크플로에 concurrency 그룹을 두고, 겹쳐도 `propose_match` 의 재검증이 이중 예약을 막는다.

### 공개 저장소의 비밀 값 규칙
- 비밀 값(Supabase service role 키, Resend API 키, VAPID 비밀 키, OAuth client secret)은 저장소에 넣지 않는다. GitHub Actions secrets, Vercel 환경 변수, Supabase Edge Function secrets 에만 둔다.
- 저장소에는 값이 빈 `.env.example` 만 둔다. `.env`, `.env.*`(`.env.example` 제외), `supabase/.temp` 는 `.gitignore` 에 넣는다.
- 커밋 전 검사로 비밀 값 스캔(gitleaks 등)을 돌리고, 같은 검사를 CI 에서도 돌린다. GitHub 의 secret scanning 과 push protection 을 켠다.
- 브라우저에 나가는 `NEXT_PUBLIC_` 변수에는 anon 키와 VAPID 공개 키만 둔다.
- 시드 데이터와 테스트 픽스처에 실제 이름·주소·전화번호를 쓰지 않는다.
- 비밀 값이 커밋됐다면 기록을 지우는 것으로 끝내지 않고 그 키를 즉시 재발급한다.

### CI 보안 규칙 (공개 저장소)
공개 저장소라 누구나 PR 을 열 수 있다. 워크플로(`.github/workflows/`)는 아래를 지킨다.

- **권한은 최소로.** 워크플로 기본 권한은 `contents: read`. 더 필요한 작업이 생기면 그 작업에만 넓히고 이유를 주석으로 적는다. 체크아웃은 `persist-credentials: false`.
- **트리거는 `pull_request` 와 `main` 푸시만.** `pull_request_target` 은 쓰지 않는다 (포크의 코드가 저장소 권한과 secrets 를 갖고 실행된다). PR 검사 작업에는 secrets 를 넘기지 않는다. 테스트는 로컬 Supabase 의 기본 키만 쓴다.
- **외부 액션은 커밋 SHA 로 고정**하고 옆에 버전을 주석으로 적는다. 태그는 다른 커밋으로 옮겨질 수 있다. 갱신은 출시 전 점검(TASKS 6.5)에서 한다.
- **같은 PR 에 새 푸시가 오면 이전 실행을 취소한다** (`concurrency`). `main` 푸시의 실행은 취소하지 않는다.
- **경로 필터(`paths`)를 쓰지 않는다.** 필수 검사가 아예 실행되지 않으면 PR 이 "대기 중" 으로 막힌다. 모든 작업이 모든 PR 에서 돈다.
- **도구 버전은 저장소 파일에서 읽는다**: Node 는 `.nvmrc`, pnpm 은 `package.json` 의 `packageManager`, Python 은 `services/matcher/.python-version`. Supabase CLI 와 uv 는 워크플로의 `env` 에 고정한다.
- **캐시**: pnpm 저장소, uv, Playwright 브라우저. 캐시 키는 잠금 파일과 도구 버전에서 만든다.
- **건너뛴 테스트는 실패다** (`scripts/check-no-skip.sh`). 예외는 `.github/skip-allowlist.txt` 에 사유와 함께 적은 것만.
- `main` 의 필수 검사: `secrets`, `web`, `matcher`, `db`, `e2e`, `prod-build`. 작업 이름을 바꾸면 브랜치 보호도 함께 바꾼다.

### 전환 기준
다음 중 하나가 되면 큐 기반으로 옮기는 ADR 을 새로 쓴다: 배치 한 번이 5분을 넘는다, 제안 지연에 대한 사용자 불만이 반복된다, 활성 사용자가 수천 명을 넘는다.
