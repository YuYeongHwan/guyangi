# 구양이 테스트 전략

무엇을 어떤 테스트로 보장하는지 정한다. 방식은 TDD (ecc:tdd-workflow).
설계 기준은 [architecture.md](architecture.md), 상태 전이는 [diagrams/exchange-state-machine.md](diagrams/exchange-state-machine.md).

## 1. 원칙

1. **테스트를 먼저 쓴다.** 실패하는 테스트를 실제로 돌려서 RED 를 확인한 뒤에만 구현한다. 쓰기만 하고 돌리지 않은 테스트는 RED 가 아니다.
2. **RED 와 GREEN 을 커밋으로 남긴다.** `test: ...` (RED 확인) → `feat:`/`fix: ...` (GREEN 확인) → 필요하면 `refactor: ...`.
3. **필수 보장(3장)은 전부 테스트가 있어야 한다.** 커버리지 수치와 별개다. 이 목록의 테스트를 지우거나 건너뛰는 변경은 리뷰에서 막는다.
4. **사고가 나는 곳을 실제 환경에서 검증한다.** RLS, 예약 수량, 상태 전이는 모의 객체가 아니라 로컬 Supabase(진짜 Postgres)에 대해 돌린다. Supabase 를 모킹한 테스트는 이 세 가지를 증명하지 못한다.
5. **테스트는 서로 독립이다.** 각 테스트가 자기 사용자와 데이터를 만든다. 실행 순서에 기대지 않는다.
6. 커버리지 기준은 6장.

## 2. 테스트 층과 도구

| 층 | 대상 | 도구 | 위치 | 명령 |
|---|---|---|---|---|
| 매처 단위 | 그래프 구성, 순환 탐색, 후보 선택 (DB 없음, 순수 함수) | pytest | `services/matcher/tests/unit` | `uv run pytest` |
| 매처 성능 | 1000명 규모 배치 시간 | pytest (`slow` 표시) | `services/matcher/tests/perf` | `uv run pytest -m slow` |
| 매처 통합 | 뷰 읽기 → `propose_match` 호출 계약 | pytest + 로컬 Supabase | `services/matcher/tests/integration` | `uv run pytest -m integration` |
| DB 통합 | RLS, 제약, 상태 전이 함수, 기한 처리 | Vitest + supabase-js + 로컬 Supabase | `supabase/tests` | `pnpm test:db` |
| 웹 단위 | zod 스키마, 구/양 표시 계산, 컴포넌트 | Vitest + Testing Library | 소스 옆 `*.test.ts(x)` | `pnpm test` |
| E2E | 핵심 사용자 흐름 | Playwright (모바일 뷰포트) | `apps/web/e2e` | `pnpm test:e2e` |

- DB 통합을 SQL(pgTAP) 대신 Vitest 로 쓰는 이유: RLS 는 "로그인한 사용자 A 의 클라이언트로 B 의 행을 읽는다" 처럼 실제 접근 경로로 확인해야 하고, 웹과 같은 러너·같은 생성 타입을 쓰면 뷰·함수 계약이 어긋날 때 타입 오류로 먼저 드러난다.
- DB 통합 테스트의 접속 정보(URL, 키)는 저장소에 두지 않는다. `supabase/vitest.config.mts` 가 실행할 때 `supabase status -o env` 에서 읽는다. 로컬 Supabase 가 떠 있지 않으면 안내 문구와 함께 실패한다.
- 무작위 입력 검증은 새 라이브러리 없이 **시드 고정 난수 생성기**로 한다. 시드 목록을 테스트에 적어 두고, 실패한 시드는 회귀 테스트로 남긴다.

## 3. 필수 보장

표의 "S" 는 그 테스트를 쓰는 스프린트다. 구현보다 먼저 쓴다.

### 3.1 매칭 엔진 (pytest, 단위)

| # | 보장 | S |
|---|---|---|
| M1 | **사이클 유효성**: 제안의 모든 leg 에서 보내는 사람은 그 아이템의 양을 갖고 있고, 받는 사람은 그 아이템이 구에 있다 | 4 |
| M2 | **사이클 유효성**: leg 들이 닫힌 순환을 이룬다. pair 는 A→B, B→A. cycle3 은 A→B, B→C, C→A. 모든 참여자가 정확히 한 번 보내고 한 번 받는다 | 4 |
| M3 | **사용자 중복 금지**: 한 제안에 같은 사용자가 두 번 나오지 않는다. 길이 3 순환으로 보이지만 실제로는 같은 사용자가 겹친 경우(A→B→A→…)를 걸러 낸다 | 4 |
| M4 | **자기 자신과의 교환 금지**: `from_user = to_user` 인 leg 가 없다 | 4 |
| M5 | **수량 초과 금지**: 한 번의 배치에서 여러 제안에 쓰인 (사용자, 아이템) 의 합이 그 사용자의 양 수량을 넘지 않는다 | 4 |
| M6 | **중복 수령 금지**: 한 번의 배치에서 같은 사용자가 같은 아이템을 두 제안에서 받지 않는다 | 4 |
| M7 | **cycle3 자격**: `can_cycle3 = false` 인 사용자는 cycle3 제안에 들어가지 않는다. pair 에는 들어갈 수 있다 | 4 |
| M8 | **재제안 금지**: 최근 7일 안에 거절·만료된 같은 leg 조합은 제안하지 않는다. 같은 두 사람이라도 아이템이 다르면 제안한다 | 4 |
| M9 | **선택 순서**: 후보는 ① 재매칭 우선권 → ② 구 우선순위 → ③ 대기 시간이 긴 순 → ④ ID 순으로 선택된다. 단계마다 앞 단계가 같은 후보 둘을 만들어 뒤 단계가 승부를 가르는지 확인한다 (테스트 4개) | 4 |
| M10 | **2단계 선택 (1:1 우선)**: 먼저 1:1 을 전부 선택하고, 남은 수량과 사용자로 3자 순환을 선택한다. 같은 아이템으로 둘 다 가능하면 1:1 이 선택된다 | 4 |
| M11 | **결정성**: 같은 입력이면 항상 같은 결과가 나온다. 입력 행의 순서를 섞어도, 여러 번 돌려도, 모든 우선순위가 같은 후보들 사이에서도(ID 순으로 갈린다) 결과가 같다 | 4 |
| M12 | **빈 입력·무매칭**: 양이나 구가 비어 있거나 가능한 교환이 없으면 빈 결과를 내고 오류를 내지 않는다 | 4 |
| M13 | **무작위 검증**: 시드 고정 난수로 만든 여러 크기의 입력에서 M1~M7 과 M11 이 항상 성립한다 | 4 |
| M17 | **막힌 3자 순환 집계**: 1:1 선택 전에는 성립했지만 1:1 이 수량이나 구를 써서 성립하지 못하게 된 3자 순환 후보 수가 실행 결과에 들어 있다. 1:1 이 없으면 0, 직접 만든 예에서는 기대한 수와 같다 | 4 |
| M18 | **후보 상한**: 한 세트의 3자 순환 후보가 상한을 넘으면 상한까지만 만들고 멈춘다. 오류를 내지 않고, 상한에 걸린 세트가 실행 결과에 기록된다 | 4 |
| M19 | **상한에서도 순서 유지**: 상한에 걸려도 남는 후보는 선택 순서(M9)가 앞선 것들이다. 우선권이 있는 사용자의 후보가 상한 때문에 잘리지 않는다 | 4 |
| M20 | **상한에서도 결정성**: 상한에 걸린 입력도 M11 을 만족한다. 다른 세트의 후보는 한 세트의 상한에 영향받지 않는다 | 4 |
| M22 | **정지된 사용자 제외**: `matchable_users` 에 없는(정지된) 사용자는 양이나 구가 뷰에 있어도 어떤 제안에도 들어가지 않는다. pair 와 cycle3 모두. 정지되지 않은 같은 입력에서는 제안이 나온다(대조군). 양·구 뷰는 정지 여부를 거르지 않으므로 매처가 걸러야 한다 (architecture.md 3.3) | 4 |

성능 (pytest, `slow`):

### 3.2 제안과 예약 잠금 (Vitest, DB 통합)

매처가 틀려도 DB 가 막는지 확인한다. `propose_match` 를 service role 로 직접 부른다.

| # | 보장 | S |
|---|---|---|
| P1 | 유효한 제안이 들어오면 매칭·참여자·leg 가 생기고, 보내는 아이템의 `reserved_qty` 가 leg 마다 1 늘어난다 | 4 |
| P2 | **예약 잠금**: 예약된 수량은 `tradable_haves` 에서 빠진다. 양이 1개인 아이템이 제안에 쓰이면 다음 조회에 나오지 않는다 | 4 |
| P3 | **수량 초과 거부**: 양 수량보다 많이 쓰는 제안은 거부되고 아무 행도 생기지 않는다 (전부 아니면 전무) | 4 |
| P4 | **동시 제안**: 양이 1개인 같은 아이템을 쓰는 두 제안을 동시에 보내면 하나만 성공한다 | 4 |
| P5 | **사용자 중복 거부**: 같은 사용자가 두 번 나오는 cycle3, 닫히지 않은 순환, `from_user = to_user` 는 거부된다 | 4 |
| P6 | **cycle3 자격 거부**: 완료 3회 미만이거나 확인된 신고가 1회 이상인 사용자가 낀 cycle3 은 거부된다 | 4 |
| P7 | 정지된 사용자가 낀 제안은 거부된다 | 4 |
| P8 | 사용자 세션(anon·authenticated)으로는 `propose_match` 를 부를 수 없다 | 4 |
| P9 | **예약 중 도감 수정**: 예약된 수량 아래로 `owned_qty` 를 줄이거나 `keep_qty` 를 올리는 수정은 거부된다 | 4 |
| P10 | 사용자는 `reserved_qty` 를 직접 바꿀 수 없다 (insert 로도 update 로도). 예약이 있는 칸은 지울 수 없다 | 2 |
| P11 | 이미 받기로 한 아이템(진행 중인 매칭의 받는 leg)은 `wanted_items` 에서 빠진다 | 4 |
| P12 | **세트 스위치를 끈 뒤**: 그 세트의 아이템으로는 새 제안이 만들어지지 않는다 (`propose_match` 가 거부). 이미 제안된 매칭과 그 예약은 그대로 남아 끝까지 진행된다 | 4 |
| P13 | **정지된 사용자에게는 매칭 제안이 가지 않는다**: 정지된 사용자가 들어간 leg 로 `propose_match` 를 부르면 거부된다. 매처 실행기를 실제 DB 로 돌려도(매처 통합 테스트) 정지된 사용자의 제안과 알림이 만들어지지 않는다 | 4 |

### 3.3 RLS (Vitest, DB 통합)

사용자 A, B, C 와 비참여자 X, 로그인하지 않은 방문자의 클라이언트를 각각 만들어 확인한다.

| # | 보장 | S |
|---|---|---|
| R1 | **타인의 도감 차단**: A 는 B 의 `collection_sets`, `collection_entries`, `wants` 를 읽을 수 없다 (0행) | 2 |
| R2 | A 는 B 의 도감 행을 만들거나 고치거나 지울 수 없다. B 의 세트 교환 스위치와 `want_mode` 도 바꿀 수 없다 | 2 |
| R3 | 방문자는 도감 테이블에서 아무것도 읽지 못한다 | 2 |
| R4 | 방문자와 사용자는 공개된 세트·아이템, 그리고 공개된 세트가 하나 이상 있는 작품만 읽고, 비공개 세트와 공개된 세트가 없는 작품은 운영자만 읽는다. 카탈로그 쓰기는 운영자만 한다 | 2 |
| R5 | 사용자는 `user_stats` 의 평판 횟수 3개를 읽을 수 있지만 쓸 수 없다. 자기 것도 못 쓴다. **A 는 B 의 `suspended_at`, `priority_since` 를 읽을 수 없다** (본인과 운영자만 `user_status()` 로 읽는다) | 2 |
| R6 | 사용자는 `admins` 를 읽을 수 없고, 자신을 운영자로 만들 수 없다 | 2 |
| R7 | 비참여자 X 는 매칭, 참여자, leg 를 읽을 수 없다 | 4 |
| R8 | **배송 정보 차단 (제안 중)**: `proposed` 상태에서 수락하며 입력한 주소는 본인만 읽는다. 같은 매칭의 다른 참여자도 읽지 못한다 | 5 |
| R9 | **배송 정보 (성사 후)**: A→B→C→A 에서 A 는 B 의 주소만, B 는 C 의 주소만, C 는 A 의 주소만 읽는다 | 5 |
| R10 | **배송 정보 차단 (같은 매칭)**: 위 순환에서 A 는 C 의 주소를 읽을 수 없다 (내가 보내지 않는 참여자) | 5 |
| R11 | 비참여자 X, 방문자, 운영자 세션은 어떤 배송 정보도 읽지 못한다 | 5 |
| R12 | 사용자는 `shipping_addresses` 에 직접 쓰거나 고치거나 지울 수 없다 (함수로만) | 5 |
| R13 | 취소·만료된 매칭의 배송 정보는 행이 남아 있지 않다 | 5 |
| R14 | 사용자는 자기 알림과 자기 푸시 구독만 읽는다. `notification_settings` 의 이메일은 본인만 읽는다 | 4·5 |
| R15 | 신고는 신고자 본인과 운영자만 읽는다. 신고당한 사람은 신고자와 내용을 읽을 수 없다 | 5 |
| R16 | `app_settings` 는 운영자만 고친다. **A 는 비공개 키를 읽을 수 없다** (`is_public` 인 키만 읽는다). 운영자도 공개 여부는 바꿀 수 없다 | 2 |
| R17 | **전수 검사**: `public` 스키마의 모든 테이블에 RLS 가 켜져 있다. 새 테이블을 RLS 없이 추가하면 이 테스트가 실패한다 | 2 |
| R18 | 뷰(`tradable_haves`, `wanted_items`, `matchable_users`)를 사용자 세션으로 읽으면 자기 행만 나온다. A 는 뷰로도 B 의 양·구를 볼 수 없고, 방문자는 아무것도 읽지 못한다 | 2 (`matchable_users` 는 4) |
| R19 | 사용자는 읽을 수 없는(비공개) 세트·아이템을 도감에 넣을 수 없고, 그때의 오류는 FK 오류(23503)가 아니라 RLS 거부(42501)다. 오류로 비공개 세트의 존재를 알아낼 수 없다 | 2 |

### 3.4 상태머신 (Vitest, DB 통합)

정상 전이:

| # | 보장 | S |
|---|---|---|
| S1 | 전원 수락 → `confirmed`, `ship_by` 설정. 일부만 수락하면 `proposed` 그대로 | 5 |
| S2 | 수락에는 배송 정보가 필요하다. 없으면 거부된다 | 5 |
| S3 | **거절 시 예약 해제**: 한 명이 거절하면 `cancelled`, 모든 leg 의 예약이 풀리고 양이 원래대로 돌아온다. 입력된 배송 정보는 삭제된다 | 5 |
| S4 | 첫 발송 표시 → `shipping`. 배송 수단이나 송장번호가 없으면 거부된다 | 5 |
| S5 | 모든 leg 수령 → `completed`. 보낸 사람은 보유 −1·예약 −1, 받은 사람은 보유 +1, 전원 완료 횟수 +1 | 5 |

### 3.6.1 교환 참여 기본값 (Vitest, DB 통합)

"도감에 기록만 한 사용자는 교환 대상이 아니다" 를 뷰 `tradable_haves`, `wanted_items` 로 확인한다 (architecture.md 3.3). 사용자 세션과 service role(매처가 읽는 경로) 양쪽에서 본다. 각 테스트는 "켜면 나온다" 대조군을 함께 둬서 빈 결과가 공허하게 통과하지 않게 한다.

| # | 보장 | S |
|---|---|---|
| G1 | **기록만 한 사용자는 양에도 구에도 없다**: 세트를 추가하고 보유 수량(3개인 칸, 0개인 칸)을 넣었지만 세트 스위치를 켜지 않은 사용자는 두 뷰 모두 0행이다. 세트 스위치의 기본값은 꺼짐이고 `want_mode` 기본값은 `all_missing` 이다 | 2 |
| G2 | **켰을 때 기본은 종류마다 하나 소장**: 스위치를 켜면 보유 1 은 양이 아니고, 보유 2 는 양 1개, 보유 3 은 양 2개, 보유 0 은 구다. 보유를 0→2 로 올리면 다른 수정 없이 양 1개가 된다 | 2 |
| G3 | **칸별 예외**: 칸을 꺼 두면(`trade_enabled = false`) 보유가 많아도 양이 아니다. `keep_qty = 0` 이면 보유 전부가 양, `keep_qty = 2`(보유 3)이면 양 1개다. `keep_qty` 를 null 로 되돌리면 기본으로 돌아간다 | 2 |
| G4 | **고른 것만 구하기**: `want_mode = 'selected'` 에서는 `wants` 에 있는 보유 0 인 아이템만 구다. 고르지 않은 빈칸은 구가 아니고, 고른 아이템이라도 보유 1 이상이면 구가 아니다. `wants` 가 비어 있으면 구는 0행이다. **대기 시간(`waiting_since`)은 고른 시각(`wants.created_at`)이다**: 칸을 나중에 고쳐도 바뀌지 않고, 사용자는 `created_at` 을 직접 쓸 수 없다 | 2 |
| G5 | **빈칸 전부 구하기**: `want_mode = 'all_missing'` 에서는 `wants` 에 없어도 빈칸 전부가 구이고, `wants.priority` 는 뷰의 `priority` 로만 나타난다 (없으면 0). 대기 시간은 칸 수정 시각, 칸이 없으면 세트 추가 시각이다 (`wants` 의 시각을 쓰지 않는다) | 2 |
| G6 | **스위치를 다시 끄면** 그 세트의 양·구가 모두 사라진다. 다른 세트(켜 둔 것)의 양·구는 그대로다. `reserved_qty` 값은 바뀌지 않는다 | 2 |
| G7 | 세트를 도감에서 빼면 남아 있는 칸은 양에 잡히지 않는다. 운영자가 세트를 비공개로 돌리면 그 세트는 양·구에서 빠진다 (service role 로 읽어도) | 2 |
| G8 | `want_mode` 는 두 값만 받는다. `keep_qty` 는 null 이거나 0 이상 보유 이하다. 실제 소장과 예약의 합이 보유를 넘는 수정은 거부된다 (23514) | 2 |

### 3.7 E2E (Playwright, 모바일 뷰포트)

| # | 흐름 | S |
|---|---|---|
| E1 | **도감**: 로그인 → 세트 추가 → 모든 칸이 실루엣 → 한 아이템의 보유 수량 입력 → 칸이 컬러로 바뀌고 구/양 수량이 보인다 → 새로고침해도 유지된다 | 3 |
| E2 | **교환 시작**: (E1 에 이어) 서로 맞는 도감을 가진 두 번째 사용자를 준비 → 매처 한 번 실행 → 매칭 탭에 제안이 보인다 → "홈 화면에 추가하고 알림 켜기" 안내가 보인다 → 배송 정보를 넣고 수락 → 상대도 수락 → 성사 화면에 내가 보낼 상대의 배송 정보가 보인다 | 5 |
| E3 | **교환 완료**: 양쪽이 발송 표시(송장 입력)와 수령 표시 → 완료 화면 → 두 사람의 도감 수량이 바뀌어 있다 | 5 |
| E4 | **거절**: 제안을 거절하면 매칭이 사라지고 도감의 양 수량이 원래대로 돌아온다 | 5 |
| E5 | 로그인하지 않고 도감·매칭 주소로 가면 로그인 화면으로 간다 | 2 |
| E6 | **테스트 로그인 경로 차단**: 운영 환경 설정으로 빌드해 띄운 앱에서 테스트 로그인 경로가 **404** 다. 테스트용 환경 변수를 실행 시점에 켜도 404 다 | 2 |
| E7 | **빌드 산출물 검사**: 운영 빌드 결과물에 테스트 로그인 라우트와 그 코드가 들어 있지 않다 (라우트 목록과 번들 문자열 검사) | 2 |
| E8 | **사용자 A 의 화면이 사용자 B 에게 보이지 않는다**: 빌드해서 띄운 앱(`next build` + `next start`, 캐시가 실제로 동작하는 상태)에서 A 로 로그인해 A 만의 값이 보이는 화면을 연 뒤, 같은 주소를 B 로 로그인해 열면 A 의 값이 없고 B 의 값이 보인다. 로그인하지 않은 방문자로 열어도 A 의 값이 없다. 화면(HTML)과 화면 전환 때 받는 데이터(RSC 응답) 둘 다 확인한다 | 2 |

**E2E 의 로그인**: 카카오·구글의 실제 OAuth 화면은 자동화하지 않는다. 테스트 계정 로그인 경로로 세션을 만든다. 이 경로는 세 겹으로 막는다.

1. **빌드에서 제외한다.** 테스트 로그인 라우트는 전용 확장자(`*.e2e.ts`)로 두고, `next.config` 의 `pageExtensions` 에 그 확장자를 E2E 빌드에서만 넣는다. 운영 빌드에서는 그 파일이 라우트로 인식되지 않아 번들에 들어가지 않는다. 실행 시점의 환경 변수 확인에 기대지 않는다.
2. **운영 Supabase 에서 이메일·비밀번호 로그인을 끈다.** 테스트 계정은 이메일·비밀번호로 로그인하는데, 이 방식은 로컬 `supabase/config.toml` 에서만 켠다. 경로가 실수로 살아 있어도 운영에서는 로그인할 수 없다.
3. **E6·E7 을 CI 에서 모든 PR 에 돌린다.** 운영 설정 빌드를 실제로 띄워 확인한다.

- 실제 카카오·구글 로그인은 출시 전 수동 점검 목록에 둔다.
- **브라우저**: Sprint 1~2 는 Chromium 모바일(Pixel 7) 하나로 돌린다. **Sprint 3 (TASKS 3.12) 부터 WebKit(iPhone) 을 추가**해 두 엔진에서 돌린다. 도감 그리드의 탭·길게 누르기 같은 터치 동작이 iOS Safari 에서 다를 수 있어서다. WebKit 은 실제 iOS Safari 와 완전히 같지는 않으므로 홈 화면 추가와 푸시는 9장의 수동 점검으로 남긴다.
- **서버**: E2E 는 `next build` 후 `next start` 로 띄운 앱에 대해 돌린다 (`apps/web/playwright.config.ts`). 이미 떠 있는 서버를 재사용하지 않는다.
- E8 은 개발 서버(`next dev`)로 돌리면 의미가 없다. 개발 서버는 캐시 동작이 달라서 통과해도 운영에서의 격리를 증명하지 못한다.
- E2E 는 다섯 개 안팎으로 유지한다. 규칙의 경우의 수는 DB 통합 테스트가 맡는다.

## 4. 환경과 데이터

- **로컬 Supabase** (`supabase start`) 를 DB 통합·매처 통합·E2E 가 함께 쓴다. 테스트 실행 전에 `supabase db reset` 으로 마이그레이션과 시드를 처음부터 적용한다. 마이그레이션이 깨지면 여기서 드러난다.
- **테스트 사용자**는 테스트마다 새로 만든다 (난수 이메일). 공용 사용자를 쓰지 않는다.
- **시각 제어**: 기한 테스트는 기다리지 않는다. service role 로 `respond_by`, `shipped_at`, `closed_at` 등을 과거로 옮긴 뒤 `run_timers()` 를 직접 부른다.
- **개인정보**: 픽스처의 이름·주소·전화번호는 누가 봐도 가짜인 값만 쓴다 (저장소가 공개다).
- **매처 단위 테스트의 입력**은 DB 가 아니라 뷰와 같은 모양의 평범한 자료 구조다. 그래서 DB 없이 빠르게 돈다.
- **합성 데이터 생성기**(1000명 규모)는 시드 고정으로 매처 테스트 안에 둔다.

## 5. CI (GitHub Actions)

| 작업 | 언제 | 내용 |
|---|---|---|
| web | 모든 PR | 건너뛴 테스트 검사 → `pnpm lint && pnpm typecheck && pnpm test` |
| matcher | 모든 PR | `uv sync --locked` → `uv run pytest` (단위) |
| db | 모든 PR | 로컬 Supabase 기동(안 쓰는 서비스 제외) → `supabase db reset` → `pnpm test:db`. `uv run pytest -m integration` 은 Sprint 4 (TASKS 4.12) 에서 넣는다 |
| e2e | 모든 PR | Playwright (빌드 후 실행한 앱), 실패 시 `playwright-report/` 와 `test-results/` 보관. **E8 은 이 작업에서 돈다** |
| prod-build | 모든 PR | 운영 설정으로 빌드가 되는지 확인. E6·E7 (테스트 로그인 경로 404, 산출물에 없음) 은 그 경로가 생기는 TASKS 2.8 에서 붙인다 |
| perf | 매처 변경 PR, 그리고 매일 1회 | `uv run pytest -m slow` (Sprint 4 에서 추가) |
| secrets | 모든 PR | 비밀 값 스캔 (ADR-0003) |

- `secrets`, `web`, `matcher`, `db`, `e2e`, `prod-build` 는 `main` 의 필수 검사다. 경로에 따라 건너뛰지 않는다. 워크플로 규칙은 ADR-0003 "CI 보안 규칙".
- RLS, 상태머신, 매칭 엔진 테스트가 실패하면 병합할 수 없다.
- 건너뛴 테스트가 있으면 실패로 본다. `scripts/check-no-skip.sh` 가 테스트 소스에서 `.skip`, `.only`, `.fixme`, `.todo`, `pytest.mark.skip`, `skipif`, `xfail`, `pytest.skip(` 을 찾아 파일과 줄 번호를 출력한다. 예외는 `.github/skip-allowlist.txt` 에 `파일경로:문자열  # 사유` 로 적은 것만 허용하고, 사유가 없는 줄은 실패다. 3장의 필수 보장 테스트는 허용 목록에 넣지 않는다.

## 6. 커버리지 기준

| 대상 | 기준 |
|---|---|
| `services/matcher` | 줄·분기 90% 이상 |
| `apps/web` 의 서버 액션, zod 스키마, 계산 로직 | 80% 이상 |
| `apps/web` 전체 | 80% 이상 (단위 + 통합) |
| DB 함수 | 수치 없음. 대신 3.2~3.4 의 보장이 전부 있어야 한다 |

- 제외: 생성된 타입(`packages/shared`), shadcn/ui 가 만든 컴포넌트, 설정 파일.
- 수치는 최저선이다. 80% 를 넘겨도 3장의 보장이 빠져 있으면 통과가 아니다.

## 7. 증거 남기기

기능 PR 본문에 아래 표를 넣는다 (스쿼시 병합으로 체크포인트 커밋이 합쳐져도 남게).

| # | 무엇이 보장되는가 | 테스트 | 종류 | 결과 | 실행한 명령 |
|---|---|---|---|---|---|
| R9 | 3자 순환에서 보낼 상대의 주소만 읽는다 | `supabase/tests/shipping-rls.test.ts` | DB 통합 | PASS | `pnpm test:db` |

- RED 를 확인한 출력과 GREEN 을 확인한 출력을 한 줄씩 붙인다.
- 돌리지 않은 테스트를 PASS 로 적지 않는다. 못 돌렸으면 그렇게 적는다.

## 8. 하지 않는 것

- Supabase 를 모킹해서 RLS·상태 전이를 "검증" 하는 테스트
- 실제 카카오·구글 OAuth, 실제 Resend·푸시 발송의 자동화
- 시각적 회귀(스크린샷 비교) 테스트 — 디자인이 자리 잡은 뒤 검토
- 부하 테스트(동시 접속) — 사용자 500명 목표에서는 매처 배치 시간만 본다

## 9. 출시 전 수동 점검 (Sprint 6)

- 카카오·구글 실제 로그인, 카카오에서 이메일 없이 가입
- iOS 에서 홈 화면 추가 후 웹 푸시 수신, 안드로이드 크롬 푸시 수신
- Resend 실제 발송, 확인 링크 인증, 스팸함 여부
- 운영 DB 에서 pg_cron 작업이 등록되어 돌고 있는지, 매처 예약 실행이 켜져 있는지
- **운영 주소에서 테스트 로그인 경로가 404 인지 직접 열어 확인**, 운영 Supabase 에서 이메일·비밀번호 로그인이 꺼져 있는지 확인
